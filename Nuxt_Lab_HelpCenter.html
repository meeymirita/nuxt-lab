1. Зачем Nuxt: чего не умеет SPA из Vue-лабы #

Откройте Helpdesk из Vue-лабы, нажмите «Просмотр кода страницы». Вот что увидит поисковик, превью в Telegram и браузер в первые сотни миллисекунд:

<body>
  <div id="app"></div>
  <script type="module" src="/assets/index-a1b2c3.js"></script>
</body>

Пустой контейнер. Всё остальное появится, когда скачается и выполнится JS, а потом придут ответы API. Для внутренней панели за логином это нормально. Для публичной базы знаний — нет:

ЗадачаSPA (Vue + Vite)Nuxt
Статью «Как настроить VPN» должен найти Googleробот получает пустой <div id="app">; часть роботов JS выполняет, часть нет, превью в мессенджерах — никогдасервер отдаёт готовый HTML со статьёй
Первая отрисовка на слабом телефонескачать бандл → выполнить → запросить API → отрисоватьHTML приходит сразу, JS «оживляет» его потом
Статьи меняются раз в неделюкаждый визит — запрос к API и рендер в браузереHTML собирается один раз на сборке и лежит файлом
Нужна форма обращения с записью в БДотдельный бэкенд (NestJS во Vue-лабе), CORS или прокси, два деплоясерверные маршруты server/api в том же проекте, один деплой
Кабинет агента за логиномидеально подходиттоже SPA: ssr: false для одной зоны

Nuxt — это Vue плюс три вещи: серверный рендеринг (тот же код компонентов выполняется на сервере и в браузере), выбор режима рендеринга для каждого маршрута и свой сервер Nitro для API. Сверху — соглашения: файловый роутинг, layouts, auto-imports, модули.

ГЛАВНАЯ МЫСЛЬ ЛАБЫ В Vue-лабе код жил в одном месте — в браузере. В Nuxt каждый компонент живёт дважды: сначала на сервере (без window, общий процесс на всех пользователей), потом в браузере (гидрация). Почти все баги Nuxt — это забытое «дважды»: запрос выполнился два раза, сервер и браузер нарисовали разное, cookie не доехала до сервера, состояние одного пользователя попало другому. Шаги «сломать → починить» построены именно вокруг этого.

2. Азбука Nuxt — каждое понятие на примере Help Center #

Двенадцать понятий, без которых не прочитать ни одного Nuxt-проекта. В сессии 1 вы напишете их руками.

2.1 Структура Nuxt 4: app/, server/, shared/

С Nuxt 4 код разделён по тому, где он выполняется:

ПапкаГде выполняетсяЧто там
app/сервер (SSR) и браузерpages, layouts, components, composables, middleware, plugins, app.vue
server/только сервер (Nitro)api, middleware, plugins, utils, БД
shared/и там, и тамтипы и Zod-схемы; нельзя импортировать ни Vue, ни Nitro
content/, public/—markdown-статьи; статические файлы как есть

Алиасы: ~ и @ указывают на app/, ~~ — на корень проекта, #shared — на shared/.

2.2 Файловый роутинг

Маршруты не описываются массивом, как во Vue Router, — их задают файлы в app/pages/. Под капотом всё тот же Vue Router.

app/pages/
├── index.vue                  → /
├── status/
│   ├── index.vue              → /status
│   └── [slug].vue             → /status/vpn
├── kb/
│   ├── index.vue              → /kb
│   └── [category]/
│       ├── index.vue          → /kb/network
│       └── [slug].vue         → /kb/network/vpn-setup      (route.params.category, .slug)
├── tickets/
│   ├── index.vue              → /tickets
│   ├── new.vue                → /tickets/new
│   └── [id].vue               → /tickets/42
└── [...slug].vue              → всё остальное (catch-all, для 404)

Параметры в квадратных скобках, [...slug] ловит любую глубину. Ссылки — через <NuxtLink to="/kb">: это RouterLink с предзагрузкой кода страницы, когда ссылка появляется в зоне видимости.

2.3 definePageMeta — настройки страницы

<script setup lang="ts">
definePageMeta({
  layout: 'agent',          // какой layout использовать
  middleware: ['auth'],     // route middleware перед входом
})
</script>

Это макрос компилятора: он извлекается из компонента на сборке, поэтому внутри нельзя ссылаться на переменные из setup.

2.4 Layouts

Обёртка вокруг страниц: шапка, меню, подвал. app/layouts/default.vue применяется ко всем страницам, другие выбираются через definePageMeta({ layout }). Место для страницы — <slot />. В app.vue стоит <NuxtLayout><NuxtPage /></NuxtLayout>.

2.5 Auto-imports

В компонентах Nuxt не нужно писать import { ref, computed } from 'vue', импортировать свои composables из app/composables/, утилиты из app/utils/ и компоненты из app/components/. В server/ так же автоимпортируются h3-утилиты и server/utils/. Магии нет: Nuxt сканирует папки и генерирует декларации в .nuxt/, отсюда IDE знает типы.

.nuxt/
├── imports.d.ts           ← все автоимпортируемые функции и откуда они
├── components.d.ts        ← глобальные компоненты
├── types/nitro-routes.d.ts ← маршруты API и типы их ответов
└── tsconfig.*.json        ← app, server, shared, node: ваш tsconfig.json просто ссылается на них
ЦЕНА АВТОИМПОРТОВ Удобно, но при чтении кода не видно, откуда взялась функция. Правило лабы: всё своё из shared/ импортируем явно через #shared/..., чтобы граница «общий код» была видна в каждом файле.

2.6 useFetch и useAsyncData

Главные composables Nuxt. Они выполняют запрос на сервере во время SSR, кладут результат в payload и не повторяют запрос при гидрации в браузере.

const { data, status, error, refresh } = await useFetch('/api/status')
// data: Ref<{ services: ...; active: ...; generatedAt: string } | undefined> — тип выведен из server/api/status.get.ts

const { data: article } = await useAsyncData(`kb-${slug}`, () =>
  queryCollection('kb').path(`/kb/${category}/${slug}`).first()
)

useFetch(url) — это useAsyncData(автоключ, () => $fetch(url)): ключ Nuxt строит сам — из места вызова в коде, URL и опций. Подробно — в разделе 5.

2.7 $fetch

Обёртка над fetch (библиотека ofetch): парсит JSON, бросает ошибку на 4xx/5xx. На сервере запрос к собственному /api/... вызывает хендлер напрямую, без HTTP. Используется в обработчиках событий (клик, submit), а не в setup для первичной загрузки — почему, покажет шаг 2.2.

2.8 useState

Общее SSR-безопасное состояние по ключу: создаётся на сервере в рамках одного запроса, сериализуется в payload, подхватывается в браузере.

const recent = useState<number[]>('recently-viewed', () => [])

2.9 Route middleware

Функции перед навигацией, аналог beforeEach во Vue Router. Файлы в app/middleware/: auth.ts подключается страницей по имени, *.global.ts — ко всем маршрутам. Выполняются на сервере при первой загрузке (и ещё раз в браузере при её гидрации) и в браузере при переходах.

export default defineNuxtRouteMiddleware((to) => {
  const { loggedIn } = useUserSession()
  if (!loggedIn.value) return navigateTo(`/login?redirect=${encodeURIComponent(to.fullPath)}`)
})

2.10 Plugins

Код, который выполняется один раз при создании Nuxt-приложения (в app/plugins/) или при старте сервера (server/plugins/, Nitro-плагины). В лабе Nitro-плагин применяет миграции БД и заливает сид.

2.11 Модули

Пакеты, которые встраиваются в сборку: добавляют composables, серверные маршруты, конфиг. npx nuxi module add auth-utils ставит пакет и прописывает его в modules. В лабе: nuxt-auth-utils, @pinia/nuxt, @nuxt/content, @nuxtjs/sitemap, @nuxtjs/robots.

2.12 nuxt.config.ts и runtimeConfig

Один конфиг на всё: модули, routeRules, настройки Nitro и Vite. runtimeConfig — значения, которые можно переопределить переменными окружения при запуске, без пересборки: runtimeConfig.dbPath ← NUXT_DB_PATH, runtimeConfig.public.supportEmail ← NUXT_PUBLIC_SUPPORT_EMAIL. Всё вне public в браузер не попадает.

3. Рендеринг под капотом: SSR → HTML → payload → гидрация #

Что происходит, когда браузер открывает /status в режиме SSR:

браузер ── GET /status ──▶ Nitro
                            │ 1. server middleware (request-id, лог)
                            │ 2. рендерер Vue: создаёт НОВОЕ приложение для этого запроса
                            │ 3. route middleware (на сервере)
                            │ 4. setup страницы: await useFetch('/api/status')
                            │       └─ вызов хендлера напрямую, без HTTP → данные
                            │ 5. renderToString → HTML
                            │ 6. данные useFetch/useState → payload (сериализация devalue)
                            ▼
браузер ◀── HTML: <div id="__nuxt">…готовая страница…</div>
             <script type="application/json" id="__NUXT_DATA__">[payload]</script>
             <script type="module" src="/_nuxt/entry.js">
   │
   │ 7. пользователь уже видит страницу (но кнопки ещё не работают)
   │ 8. JS скачан: Vue создаёт приложение, читает payload
   │ 9. setup выполняется СНОВА: useFetch находит данные в payload по ключу → запроса нет
   │10. гидрация: Vue проходит по готовому DOM, сверяет с виртуальным деревом,
   │    навешивает обработчики событий — DOM не пересоздаётся
   ▼
интерактивная страница; дальнейшие переходы — как в обычной SPA

Три вывода, на которых стоит вся лаба:

  1. setup выполняется дважды — на сервере и в браузере. Всё, что в нём делается, делается два раза, если специально не позаботиться (шаг 2.2).
  2. Гидрация требует совпадения. Если сервер нарисовал «Обновлено в 12:00:01», а браузер при гидрации посчитал «12:00:03», Vue видит расхождение: hydration mismatch (шаг 2.5).
  3. Сервер — один процесс на всех. Приложение Vue создаётся на каждый запрос заново, а модули JS — нет. Переменная на уровне модуля живёт между запросами разных пользователей (шаг 4.4).

🔬 Под капотом: что такое payload и почему JSON и payload сериализуют по-разному

Payload — это данные всех useAsyncData/useFetch/useState одного рендера. Nuxt сериализует его библиотекой devalue, а не JSON.stringify: devalue умеет Date, Map, Set, BigInt, циклические ссылки и ref. Поэтому, если useAsyncData вернул new Date(), в браузере будет настоящий Date.

Ответ API-маршрута — другое дело. Хендлер server/api/*.ts отвечает по HTTP, и тело сериализуется в обычный JSON: Date превращается в ISO-строку. Даже на сервере, где useFetch вызывает хендлер без сети, Nuxt имитирует тот же контракт. Выведенный тип это знает: если хендлер возвращает { startedAt: Date }, у data.value.startedAt будет тип string. Оба случая вы увидите рядом в шаге 2.1.

Посмотреть payload можно в DevTools: вкладка Elements, <script id="__NUXT_DATA__"> в конце body. Это плоский массив, где объекты ссылаются друг на друга по индексам — так devalue экономит место на повторах.

4. Режимы рендеринга и routeRules #

Nuxt не заставляет выбрать один режим на всё приложение. Правила задаются по маршрутам в routeRules:

export default defineNuxtConfig({
  routeRules: {
    '/':          { prerender: true },   // SSG: HTML собирается на сборке
    '/kb':        { prerender: true },
    '/kb/**':     { prerender: true },
    '/status':    { swr: 60 },            // SSR + кеш на 60 с, обновление в фоне
    '/agent/**':  { ssr: false },         // SPA: сервер отдаёт пустую оболочку
    // /tickets/** — правил нет, значит SSR на каждый запрос (по умолчанию)
  },
})

В лабе сборка запускается как обычный node-сервер, и там isr ведёт себя как swr: кеш живёт в памяти процесса Nitro. Поэтому в заданиях используется только swr, а ISR остаётся на «Что дальше».
🔬 Под капотом: prerender и поиск — почему на готовом HTML нельзя искать «на сервере»

Пререндеренная страница — это файл .output/public/kb/index.html, собранный на этапе nuxt build. Когда пользователь откроет /kb?q=vpn, сервер отдаст тот же файл: query-параметр в момент сборки не существовал, и рендера на запрос нет. Значит, всё, что зависит от ввода пользователя, на такой странице выполняется в браузере: после гидрации страница сама обращается к API. В лабе поиск по базе знаний — это server route /api/kb/search, который браузер вызывает при вводе (шаг 5.2). Сам маршрут API не пререндерится и работает на каждый запрос, с кешем.

5. Данные: useFetch, useAsyncData, $fetch #

5.1 Что делает useAsyncData

На сервере: вызывает функцию, ждёт результат, кладёт в payload под ключом. В браузере при гидрации: находит ключ в payload и отдаёт данные без вызова. При клиентском переходе на страницу: payload нет — вызывает функцию в браузере.

Ключ — это идентичность данных. Два вызова с одним ключом делят один результат (дедупликация). У useFetch ключ строится автоматически — из места вызова в коде (файл и порядковый номер вызова), URL и опций: два useFetch('/api/status') в разных строках получат разные ключи, и чтобы они делили данные, ключ задают явно (key: 'status'). У useAsyncData вы задаёте его сами — и отвечаете за уникальность: useAsyncData('article', ...) на двух страницах статей будет отдавать одну статью.

NUXT 4 С Nuxt 4 data и error до загрузки равны undefined (в Nuxt 3 был null), а data — это shallowRef: мутация вложенного поля data.value.items.push(x) не перерисует шаблон. Меняйте данные заменой: data.value = { ...data.value, items: [...] } или через refresh().

5.4 Ошибки

На сервере: throw createError({ statusCode: 404, statusMessage: 'Сервис не найден' }) — Nitro превращает это в HTTP-ответ с этим кодом. В странице: useFetch не бросает, а кладёт ошибку в error. Если без данных страница не имеет смысла, бросьте её дальше: throw createError({ ...error.value, fatal: true }) — Nuxt покажет app/error.vue с правильным HTTP-статусом (для SEO это важно: 404 должна быть 404, а не 200 с текстом «не найдено»). Выйти со страницы ошибки — clearError({ redirect: '/' }).

6. Nitro — сервер внутри проекта #

Nitro — серверный движок Nuxt. Он же рендерит страницы, он же обслуживает API. Файл в server/api/ = маршрут, метод берётся из суффикса имени:

server/api/status.get.ts              → GET    /api/status
server/api/tickets/index.post.ts      → POST   /api/tickets

Хендлер — функция от события event (объект h3). Что вернули — то и ответ: объект сериализуется в JSON.

// server/api/tickets/[id].get.ts

Кеширование

7. Состояние на SSR: почему модульный ref опасен #

Во Vue-лабе такой код был нормальным:

// composables/useRecentlyViewed.ts
const recent = ref<number[]>([])                 // ← на уровне модуля
export function useRecentlyViewed() { return recent }

В браузере модуль загружается один раз на вкладку — одна вкладка, один пользователь. На сервере Nuxt модуль загружается один раз на процесс, а процесс обслуживает всех. Борис открыл обращение №7 — recent стал [7]. Вера открывает любую страницу — сервер рендерит её с тем же recent, и в HTML Веры появляется «Вы недавно смотрели: №7». Это не теоретический риск, а классическая утечка данных.

Где хранитьЖивётSSR-безопасноКогда
ref внутри setup компонентапока жив компонентдалокальное состояние
ref на уровне модулявесь процесс сервера❌ общее для всех пользователейтолько в коде, который гарантированно работает лишь в браузере
useState(key, init)один запрос на сервере → payload → браузердапростое общее состояние: пара значений
Pinia (@pinia/nuxt)один запрос → payload → браузерда (store создаётся на каждый запрос)состояние с действиями и геттерами

callOnce(key, fn) — выполнить инициализацию один раз: на сервере при SSR, и не повторять при гидрации. Удобно для заполнения store данными, которые не нужно держать в useFetch.

8. Авторизация: сессия в cookie #

nuxt-auth-utils хранит сессию в зашифрованной cookie (sealed cookie): данные пользователя лежат прямо в cookie, зашифрованные ключом NUXT_SESSION_PASSWORD. Серверу не нужна таблица сессий, а клиент не может ни прочитать, ни подделать содержимое.

ГдеAPIЧто делает
серверsetUserSession(event, { user })записать сессию (после проверки пароля)
серверrequireUserSession(event)вернуть сессию или бросить 401
серверhashPassword / verifyPasswordхеш scrypt для таблицы users
клиентuseUserSession()loggedIn, user, fetch() (перечитать), clear() (выйти)

Тип пользователя расширяется через declaration merging — один раз, и user.role типизирован везде, на сервере и клиенте:

// shared/types/auth.d.ts
import type { Role } from '#shared/types/domain'
declare module '#auth-utils' {
  interface User { id: number; email: string; name: string; role: Role }
}

Главная ловушка: cookie при SSR

Браузер отправляет cookie в запросе за страницей. Дальше страница на сервере делает внутренний запрос к /api/tickets. Этот внутренний запрос — новый, и cookie в нём нет, если их не переложить явно. useFetch и useRequestFetch() перекладывают заголовки входящего запроса сами, голый $fetch — нет. Итог: страница «Мои обращения» при прямом открытии получает 401, а при клиентском переходе работает (в браузере cookie отправляются автоматически). Такой баг не заметить в разработке, если всегда ходить по ссылкам — шаг 4.3 ловит его специально.

ЗАЩИТА — НА СЕРВЕРЕ Route middleware только управляет навигацией: не пускает на страницу и делает редирект. Данные защищает requireUserSession в API. Проверка роли только в middleware — это дыра: любой может вызвать /api/agent/tickets через curl.

9. Контент и SEO: Nuxt Content, sitemap, robots #

Nuxt Content v3 превращает папку content/ с markdown-файлами в типизированную коллекцию, которую можно запрашивать как базу данных. Коллекции описываются в content.config.ts со схемой frontmatter на Zod, поэтому у результата запроса есть TypeScript-тип.

// в странице (браузер или SSR)
const { data } = await useAsyncData(`kb-${path}`, () => queryCollection('kb').path(path).first())

// в server route — с event первым аргументом
const items = await queryCollection(event, 'kb').select('title', 'description', 'path').all()
ДВЕ SQLITE У Nuxt Content своя база SQLite (.data/content/contents.sqlite): на сборке markdown парсится и складывается туда, а в продакшене база восстанавливается из дампа, вшитого в сборку. У приложения — своя SQLite через Drizzle (.data/app.sqlite): пользователи, обращения, сервисы. Это две разные базы с разными жизненными циклами: первая пересоздаётся при каждой сборке и в git не хранится, вторая — рабочие данные, её нужно сохранять между деплоями (docker volume).

SEO в лабе — четыре вещи. useSeoMeta() ставит title, description и OG-теги с проверкой типов. Canonical — через useHead. @nuxtjs/sitemap генерирует /sitemap.xml из статических страниц и из коллекции Content. @nuxtjs/robots генерирует /robots.txt и закрывает от индексации личные зоны. Оба модуля читают адрес сайта из общего site: { url } в конфиге.

🔬 Под капотом: чем опасен mismatch, кроме предупреждения

В продакшене Vue не выводит подробный warning, а молча чинит расхождение: для текстовых узлов — заменой текста, для структурных (разное количество элементов, другой тег) — пересозданием поддерева. Это стоит производительности и может сбросить состояние (фокус, введённый текст). Хуже, если расхождение в атрибутах, например :class или :disabled: они могут остаться серверными. Типичные источники mismatch: Date.now(), Math.random(), часовой пояс, localStorage в шаблоне, проверка window.innerWidth для выбора разметки, невалидный HTML (<div> внутри <p>: браузер перестраивает его до гидрации). 13. Глоссарий #

SSR (Server-Side Rendering) — рендеринг HTML страницы на сервере на каждый запрос.
CSR (Client-Side Rendering) — рендеринг в браузере; сервер отдаёт пустую оболочку. В Nuxt — ssr: false.
SSG / prerender — HTML собирается один раз при nuxt build и отдаётся файлом.
SWR (stale-while-revalidate) — отдавать закешированную версию, а после истечения срока обновлять её в фоне; первый запрос после истечения получает старую.
ISR — инкрементальная регенерация на CDN платформы (Vercel, Netlify); на node-сервере ведёт себя как SWR.
Гидрация (hydration) — «оживление» серверного HTML в браузере: Vue сверяет DOM с виртуальным деревом и навешивает обработчики, не пересоздавая разметку.
Hydration mismatch — расхождение между HTML сервера и тем, что браузер отрисовал бы при гидрации.
Payload — данные useAsyncData/useFetch/useState/Pinia одного рендера, переданные в HTML в __NUXT_DATA__.
devalue — сериализатор payload; в отличие от JSON сохраняет Date, Map, Set, циклы.
Nitro — серверный движок Nuxt: рендер страниц, API, кеш, плагины, сборка в .output.
h3 — HTTP-фреймворк внутри Nitro: event, defineEventHandler, getQuery, readBody, createError.
Server route — файл в server/api/, который становится HTTP-маршрутом; метод — суффикс имени.
Server middleware — функция в server/middleware/, выполняется перед каждым запросом к Nitro.
Route middleware — функция в app/middleware/ перед навигацией; на сервере при первой загрузке, в браузере при переходах.
Nitro-плагин — код в server/plugins/, выполняется один раз при старте сервера; Nitro не ждёт асинхронные плагины.
Auto-imports — функции и компоненты, доступные без импорта; декларации генерируются в .nuxt/.
routeRules — правила по маршрутам в nuxt.config.ts: режим рендеринга, кеш, заголовки, редиректы.
runtimeConfig — конфигурация, переопределяемая переменными NUXT_* при запуске; public доступна в браузере.
useFetch / useAsyncData — загрузка данных с выполнением на сервере, передачей через payload и ключом для дедупликации.
$fetch — функция запроса (ofetch); на сервере для своих маршрутов вызывает хендлер без сети, но без cookie входящего запроса.
useRequestFetch — $fetch, пробрасывающий заголовки входящего запроса при SSR.
useState — SSR-безопасное общее состояние по ключу, живёт в рамках запроса и передаётся в браузер.
callOnce — выполнить функцию один раз: на сервере при SSR, без повтора при гидрации.
Sealed cookie — cookie с зашифрованными и подписанными данными сессии; клиент не может прочитать или подделать содержимое.
Declaration merging — дополнение интерфейса из чужого модуля (declare module '#auth-utils', 'h3').
Drizzle ORM — ORM с описанием схемы на TypeScript и типобезопасными запросами; drizzle-kit генерирует SQL-миграции.
Nuxt Content — модуль, превращающий markdown в типизированные коллекции в своей SQLite; запросы через queryCollection.
Ключ кеша — строка, по которой Nitro хранит закешированный ответ; должна включать всё, от чего зависит ответ.
Canonical — <link rel="canonical">, основной адрес страницы для поисковика.
Soft 404 — страница «не найдено» с кодом 200; вредит индексации.
Краулер пререндера — обход ссылок при сборке для поиска страниц к пререндеру; ограничивается через ignore.
.output — результат nuxt build: public/ (статика и пререндер) и server/ (Nitro с трассированными зависимостями).
